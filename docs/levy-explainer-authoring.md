# Levy explainer modal — internal authoring notes

Internal reference while we build. Not user-facing; do not link this from `/sources` or ship it as product copy.

This doc applies **only** to data and copy for the levy explainer slice of the **levy line detail** dialog. General **information hierarchy** (primary first, supporting detail below) for the whole app is in `.cursor/rules/base-rule.mdc`. **Levy line detail** behavior, explainer JSON, and tone live **here** so rules files stay short cross-references.

Not every levy row has entity-specific JSON; the pattern below still governs the shell (taxing authority, IDs, contact, disclosures) and any explainer block.

## Modal pattern (levy line detail)

These apply to the levy detail dialog and optional explainer content (same UX goals as other modals: scannable first screen, depth on demand).

- **Essentials first:** Open with what the user came for (identity of the row, key numbers, primary actions). Do not lead with methodology, naming history, or long disclaimers.
- **Dig without dumping:** Put statute text, long citations, registry nuance, and fine print behind collapsible regions (`<details>`), accordions, or links (e.g. `/sources`, external official pages). The default view should stay scannable on a phone.
- **Not every row needs custom explainer JSON:** The pattern (short surface, optional depth) applies whether or not a levy has an explainer entry.
- **One job per band:** Avoid saying the same story three times in stacked sections (e.g. government level + body copy + links). Classify once, summarize briefly, link or collapse the rest.

  - **Tone (authority chain):** Short and bill-centered. **Resident impact first:** lead with how the vote or rate change affects the person reading (their bill, their money, what they pay or what the government must return to them). Mechanism and labels come second. **Accuracy over brevity:** do not drop a needed qualifier to sound punchy (for example, name a temporary tax credit and the TABOR keep-limit reason; do not say a government simply "cut the rate"). One main idea per step. **openGaps** are for residents (honest limits on what we can claim), never authoring notes, missing-file hunts, 404s, or pipeline talk. Put lasting missing-document hunts in `src/content/authorityChainUnlocatedSources.ts` (see `docs/authority-chain-unlocated-sources.md`); scratch only in `docs/_working/`.
  - **Next-best source (core ideology):** Always cite the **best official document you can honestly use**. Prefer Notice of Election / TABOR PDF, then English sample ballot, then a **Spanish sample ballot when that is the only ballot wording we can link among the county's currently published files** (see **Spanish sample rule** below), then Official Summary, then that year's Past Elections File Library (or similar hub). When the ideal file is missing, wrong language, or dead, **do not leave a blank fact and do not invent a 404 path**. Link the **next best official place** so the resident can see **where we looked** and **why** the best document is not there. Honest labels matter (for example "County sample ballot (Spanish)" or "Not available in county election files" plus a file-library hub). Pair that with an **openGap** when residents need the limit explained under **What we can't say for sure**. Also add or update a row in `AUTHORITY_CHAIN_UNLOCATED_SOURCES` so `/sources` can list remaining blockers (for example still-missing English Notice/sample) under **Official documents we could not find**. Frame findability as **what we can locate today** among published files; do **not** imply an English ballot never existed.
  - **Official sources (stability first):** Prefer **stable** county or district URLs residents can still use months later. **Deep-link** to the exact PDF when the URL is reliable and you have verified the file (vote totals, ballot wording). When a PDF path is brittle, rotates, or the Official Summary row does not name the district (only "Ballot Issue 4C"), a **county election file library** or similar **official hub** is acceptable. Label the link honestly (for example "2020 election files" or "Past Elections File Library") so users know they may need to open the right year's folder or summary themselves. Perfect one-click jumps are not required; **working links beat dead deep-links**. Still do **not** cite Clarity Election Night Reporting SPA URLs (`results.enr.clarityelections.com/...`); cold deep links often fail and IDs rotate. Durable unlocated-document rows live in `src/content/authorityChainUnlocatedSources.ts`, not only in ephemeral working docs.
  - **County overlays (registry-linked):** Shared authority-chain entries use county-neutral base JSON (`match.registryId`). County-specific closed-summary notes, tax-list names (`countyListName`), and open gaps go in `countyOverlays`, keyed by wired county id. The builder merges overlays when `findLevyAuthorityChainEntry` passes the resident `countyId` and stack `authorityLabel`. Do not put `summary.summaryClosingNote` on registry-linked entries; use `countyOverlays` only.
  - **Resident-county gating (mills / rate tables):** AUTH-derived What changed? facts and Levy % PDF links use **only** the resident county's bundled mills when `CountyConfig.features.millsHistory` is true for that county. When false (Douglas today), show `mills.stepBody` narrative only and add `no-resident-county-mills-history` (or equivalent) via `countyOverlays` — **never** substitute another county's rate tables or AUTH series. `resolveAuthorityMillsLookup` and `LevyAuthorityChainSection` take `countyId`; deep-link AUTH is the resident stack code, not `millsReferenceCountyId`.
  - **Attribute reported outcomes:** do not present an election result as independently verified by this app. Start with plain attribution such as "According to Arapahoe County's certified election results..." for single-county school/county entries, or a **county-neutral** lead such as "According to official certified election results" when the same authority-chain entry serves multiple counties via `match.registryId`. Use `summarySource` to link that phrase to the **best stable official record** for the claim (county canvass PDF, state filing, or other first-party source). `summarySource.text` must match the built summary phrase exactly: no leading or trailing whitespace. School/county summaries use `headlineIssues`; metro summaries may use `headlinePlain` when no public ballot letter exists. Metro actor language is **eligible electors**, with an in-flow definition. Do **not** append unsourced governance closers. Ballot-issue highlights are derived only from actual `headlineIssues` / `also`; never invent a metro Ballot Issue letter to create one. Optional `summary.summaryClosingNote` (or `countyOverlays.{countyId}.summaryClosingNote` for shared entries) appends an always-visible second paragraph as `NOTE: …` (omit the `NOTE:` prefix in JSON; the builder adds it). Use that for a short, neutral source caveat that belongs in the closed summary (for example, preferred county Notice PDF not currently available, so the Ballot Issue link uses another coordinating county's Notice for the same district measure). Do not put HTTP status language or authoring hunts in that note.
  - **E2E:** `e2e/authority-chain.spec.ts` is tax-authority-agnostic. Adding an entry with `match.levyLineCode` automatically adds a panel UI case. Do not hard-code district prose in the spec; expected titles, gaps, and `href`s come from this JSON. Live curated-source reachability is a separate `@live-sources` test (`e2e/authority-chain-live-sources.spec.ts`, `npm run test:e2e:live-sources` / manual workflow) so third-party hosts do not fail PR e2e or look like a panel regression. For Assessor PDF deep-links, prefer `files.arapahoeco.gov/...` (the durable file host); `www.arapahoeco.gov/Assessor/...` often only redirects and can 403 datacenter probes.
  - **Define jargon in place, do not jump:** to gloss one word or phrase in a step `title` or `body`, or in the entry `summary`, set `titleTermId`/`titleTermMatch`, `bodyTermId`/`bodyTermMatch`, or `summaryTermId`/`summaryTermMatch`. Extra body glosses on the mills step use pack defaults or entry `mills.bodyTerms` (e.g. TABOR plus mill levy). Allowed ids live in top-level JSON `allowedInlineTermIds` (including `term-eligible-electors` for metro authorization copy). It renders a brief popover on that text, not a jump to the modal footer. The validator checks each id is allowed, resolves a flow glossary brief, and checks that the phrase appears in the chosen field. Jargon with a calm in-place definition is intentional education; undefined insider words are the failure mode.
  - **PDF deep-links and ballot-text ladder:** When the cited claim lives on a specific page of a stable PDF, prefer `#page=N` after you verify the **PDF viewer page index** (often not the printed page number; open the file, for example with `pdfplumber`, rather than trusting a table of contents). A PDF URL without `#page=` still opens the correct document; the viewer starts at page 1. That is an honest fallback, not a broken link. Do **not** invent a page number to avoid page 1. **Resident-facing link text names the document** (or the library), not "opens to page N." County Levy Percentage / rate-table PDFs need runtime context because they are indexed by tax area and one authority can appear on hundreds of pages. Authority-chain rate-table links therefore use the open parcel's `tagShortDescr` (zero-padded to the PDF TAG), tax year, and AUTH to append the exact page from `arapahoe-authority-rate-table-pages.json`. TAG alone is not enough because one tax-area group can cross a page boundary. If an older PDF lacks that current TAG + AUTH combination, keep the correct year PDF without a fragment rather than guessing (same page-1 fallback). Regenerate both authority-mills files when adding a curated entry. Ballot wording ladder (same spirit as **Next-best source**): (1) county **Notice of Election** / TABOR notice with `#page=` when verified, (2) English sample ballot, (3) Spanish sample when that is the only ballot wording we can link among currently published county files (see **Spanish sample rule**), (4) `ballotTextKind: "unavailable"` with file-library hub + `no-stable-ballot-text`. Do **not** invent a 404 PDF path.
  - **Spanish sample rule (locked):** If a live county Spanish sample ballot is the only official ballot wording we can **link today** among currently published files, **use it**. Do **not** pretend there is no ballot text, and do **not** refuse the Spanish PDF just because English is missing from those files. Do **not** imply an English ballot never existed (an election years ago almost certainly had English; we are stating findability on the county site today). Document thoroughly so residents cannot confuse help text with legal English ballot language: (1) `ballotTextKind: "sample_ballot"`, `ballotTextLanguage: "es"`, `ballotTextEnglishSource: "ai_translation"`; (2) `ballotTextSource` links the Spanish PDF; fact value **County sample ballot (Spanish)**; (3) `ballotTextEnglishHuntSource` links that year's Past Elections File Library hub; the built step links the "We could not locate an English…" sentence to that hub; (4) measure `detail` is AI-translated substance that tracks the Spanish PDF (punctuation/structure faithful; no pack closers like "That is a mill levy, not a bond" inside the translation); (5) short intro in the step body (*We could only locate a sample ballot in Spanish* + linked English-not-located sentence) and AI English behind a **collapsed-by-default** nested disclosure (`bodyDisclosure`, label from `AUTHORITY_CHAIN_AI_TRANSLATION_DISCLOSURE`; body is translation in a blockquote only; caveats on the label, not duplicated inside); (6) openGap `ballot-text-spanish-only-ai-translation`; (7) keep an `AUTHORITY_CHAIN_UNLOCATED_SOURCES` row for the still-missing English Notice/sample. Prefer English Notice / English sample when they appear later, then drop AI translation. **Never** present AI English as official English ballot text, a county English translation, or the legal English wording of the measure.
  - **Hard-facts when ballot text is missing:** When nothing usable can be linked: `unavailable` means **omit** `detail`; use a live official hub or next-best record and put official restatements in `supportingFacts` / `budget`. School/county use `no-stable-ballot-text`. Metro uses `metro-election-records-unlocated`, optional `ballotIssue`, and an `approval` record instead of vote totals when no tally is public. Metro validation requires either complete `votes` + `resultsSource` or a cited `approval`; it never accepts placeholders. When metro ballot wording is unavailable but cited approval evidence exists, the builder omits a duplicate "Election record / wording not located" fact; the step body and open gap already explain that limit. English school/county ballot framing only applies when legal wording is linked. Do not silently join a vote label and a budget statement into a claim the sources do not make.
  - **Issuer-owned hosts (and issuer-published files):** fact and summary source URLs must be the county, the taxing authority, another official government host (for example `arapahoeco.gov`, `arapahoevotes.gov`, `littletonpublicschools.net`, `cherrycreekschools.org`, `ssprd.org`, `leg.colorado.gov`), or the **document file URL the issuer publishes** from its own site (some districts only host PDFs on their CMS CDN, e.g. Thrillshare `files-backend.assets.thrillshare.com/.../Lps/...`). Prefer a first-party hostname when one exists. Do **not** cite unrelated third-party mirrors or scrapers (readkong, random document hosts, news reprints). Prefer a verified PDF deep-link when stable; otherwise an official hub or district page that still resolves is fine.
  - **Standard step shape (master trail):** Who gets this money? → What changed? → one step per sourced authorization (metro may add a later `metro_commitment` such as a capital pledge) → approval evidence appropriate to the authority family → optional budget step → openGaps. School/county/fire normally show a separate **How people voted** step from certified totals. Metro folds `approval` or vote facts onto each measure step so the trail stays chronological (no trailing duplicate authorization dump). The family pack changes the evidence criteria and nouns; it does not remove master trail pieces. The mills-over-time chart remains a **separate** UI module.
  - **Metro / fire What changed? (AUTH-derived):** Do **not** hand-author `currentMills` / `priorMills` / `historicalComparison` on metro or fire entries. Build derives facts from the same AUTH mills-over-time series the modal chart uses (`arapahoe-authority-mills-by-tax-year.json` via `selectMetroAuthorityMillsChangeBlocks` in `authorityMillsChangeBlocks.ts`; gated by `usesAuthDerivedMills`):
    - Always: labeled **Change from last year** (latest adjacent published pair).
    - Also: **Most notable change** when another adjacent pair has a larger absolute mill move; if the largest move *is* last year, omit the second block. Absolute ties prefer the more recent pair.
    - Levy % PDF cites come from `_meta.sources[].residentUrl` on `arapahoe-authority-mills-by-tax-year.json` (regenerated via `tools/extract_authority_mills_by_tax_year.py`). Never invent a missing year or 404 path.
    - Optional `mills.stepBody` is a short bill takeaway only. Do not narrate Change from last year / Most notable selection rules in the trail body; that methodology lives on `/sources`.
  - **Closed summary vs opened trail:** Summary answers **Who authorized this?** (who + brief when/how). Do **not** put Change from last year / Most notable change in the closed blurb; those blocks are for the opened **What changed?** section. Never imply voters or eligible electors re-voted on each annual mill tweak unless a cite says so.
  - **Cite link text:** Reusing the same PDF URL (even the same `#page=`) is fine when **visible link text differs**. Avoid identical text + identical URL twice.
  - **Repeated figures:** When separate official actions use the same number, keep the actors and legal meanings separate, use one readable number format, and say plainly why the later fact is not a duplicate (for example, an elector-approved tax ceiling versus a county-approved aggregate debt cap). Metro measure facts render approval before later `supportingFacts` so chronology stays readable.
  - **Family packs:** Each JSON entry declares `family` (`school` | `county` | `metro` | `fire`). The builder picks a pack for reusable authorization titles/bodies, approval evidence labels, budget labels, and default mills chrome. School kinds: `override`, `bond`, `debt_free_mill`. County kind: `tabor_revenue_retention`. Metro kinds: `bond`, `operations_mill`, `tabor_revenue_retention`, `metro_authorization` (documented authorization without a public Ballot Issue letter), and `metro_commitment` (later district pledge/financing action; plain `detail` body; not an eligible-elector lead). Fire kinds: `bond`, `operations_mill`, `tabor_revenue_retention` (coordinated Ballot Issue + county certified votes; Voters language; AUTH-derived What changed?). Metro measures require `titlePlain`; `ballotIssue` is optional on authorization-style measures and must be omitted on `metro_commitment`. Fire measures require `ballotIssue` and `titlePlain`. School/county/fire measures require certified vote totals; metro measures require either published totals or a cited official `approval` record (folded onto each measure step), never both, and never placeholders or invented ballot labels. Optional budget facts use `budget`; entry-specific recipient facts use `authority.whoGetsBody` / `whoGetsFacts`. Missing school/county ballot wording uses `no-stable-ballot-text`; metro uses `metro-election-records-unlocated` plus the best official district record available. Multi-county fire districts that cite Arapahoe tallies only use `multi-county-arapahoe-votes-only`. The Spanish/AI ladder remains a one-off county fallback (see Spanish sample rule above). Durable missing-document hunts live in `src/content/authorityChainUnlocatedSources.ts`. Keep the shared trail; do not fork a second builder.

One-sentence terms can stay popover-only.

## Tone and voice (levy explainer copy)

Resident-facing strings in `levy-explainer-entries.json` should feel **friendly and accessible**: plain English, low bureaucracy, written for someone who pays the bill and wants to understand **who** and **why**, not for a legal brief.

- **Human first:** Explain renames, splits, or stale labels the way you would to a neighbor (e.g. *they rebranded*, *older legal name*, *your bill can read differently from the website*). Say what actually happened (rebrand, same agency, not a merger) when that removes confusion.
- **Not government-first:** Do not lead with statute voice (*pursuant to*, *the entity is known as*) in **What is it?**; put formal framework and PDFs in **citations**. It is fine to mention law or county tables when it helps (*state law still uses…*, *county tax labels*), but keep the sentence about **people and names**, not about code sections.
- **Do not bury the lede in links only:** If a taxpayer would feel misled without knowing something (e.g. two names, one district), say it in a **short** visible paragraph; use links for depth and history, not as the only place the truth appears.
- **Punctuation in explainer JSON:** Prefer commas and periods. **No em dashes** in resident-facing strings; `npm run validate:levy-explainer` rejects U+2014 (same spirit as levy line detail shell copy in `LevyLineDistrictDetailDialog.tsx`).
- **Reference shape:** See **`urban-drainage-south-platte-levy`** for rebrand / old legal name vs public name in conversational prose, with statute and district links in **citations** only.

App-wide audience and plain-language rules remain in `.cursor/rules/base-rule.mdc`. This section is the canonical guide for **levy explainer JSON** tone.

## Levy line detail modal (shared chrome, all rows)

Applies to **all** levy tiles — not entity-specific. Keep wording **plain** and **parallel** across the app.

- **Stack label fidelity (locked):** The levy **tile title** and modal **taxing authority** heading must match that county's stack line `authorityName` from ingest (after `displayMartAuthorityName` title-case only). Residents compare the app to their county levy stack line by line; do not rename, abbreviate, or normalize shared districts to one spelling across counties in stack UI. Curated names in authority-chain JSON or the cross-county registry are for **Who authorized this?** only, not a replacement for the stack label.
- **Order:** Taxing authority name → tax entity / LG ID → optional **LG ID vs contact** note → optional medium-confidence note → Contact (website, address) → footnotes.
- **LG ID mismatch (bill vs directory):** Short lead-in that **Contact** comes from a **different public listing ID** than the bill; avoid jargon like **registry row** or **registry mail** in user-facing strings. Longer explanation lives in a **`<details>`** with a **visible chevron** (rotates when open). **Coarse types** (no per-entity one-offs): `levyGovernmentContactKind()` in `src/lib/levyGovernmentKind.ts` returns **`special_district_context`** vs **`other`** (county, school, city, state, etc.) from explainer `origin.level` when present, else authority label. **Shared** first and last paragraphs in the disclosure; **second** paragraph and **Contact** footnote **branch** so special districts can mention **administrative mail**, **shared** listings, and **third-party administrators** without implying a county building is a private firm. **`other`** copy stresses **another government** office, **shared public** building, and **administrative** mail. **No em dashes** in this shell copy (commas / periods only). Use explicit `{" "}` in JSX after `</strong>` / inline elements so spaces do not collapse.
- **Do not** tell users to "use your bill name" as if they had not already seen the name — they have. Contrast **taxing authority** (this levy) vs **Contact** (how the directory lists phone/mail), without implying the tile title is in doubt.
- **JSON explainers** (`levy-explainer-entries.json`) stay entity-specific where needed; **district/contact shell** copy stays **generic** so we do not maintain ad hoc strings per district in the dialog component.

### Voter-facing facts that are not contact-ID mismatch (rebrand, legal vs public name, etc.)

- The levy **explainer block** (`LevyExplainerModalSection` in `LevyLineDistrictDetailDialog.tsx`) is the right place for **entity-specific** copy that helps someone investigate **what government this is** (e.g. why two levy rows exist for one program). **No new modal section is required**; use `whatIsIt.paragraphs` and **citation links** (`citationBlocks`, optional `afterLinksNote`) for depth. **Do not** use `origin` for branding or rename stories, only for **type** (see `origin.detail` below).
- Keep **visible** copy short: government level + one or two tight **What is it?** paragraphs. Put essays, naming history, and supporting docs in the **More detail and sources** accordion and links, not repeated across `origin`, `whatIsIt`, and citations.
- That is separate from the **shared** LG ID / directory / contact disclosure, which stays coarse and generic in `LevyLineDistrictDetailDialog.tsx` (`levyGovernmentContactKind`, mismatch `<details>`, etc.).
- It is normal for those voter facts to be **one-off prose per entry** in JSON (each levy row with an explainer match can say what residents need for that row).

## Government level (`origin`)

- **heading** — Keep as `Government level` unless we decide to change the pattern app-wide.
- **level** — Short label for the kind of government (e.g. `Library district`, `Local levy (state program)`). Must match the row.
  - **Do not use bare `State`.** Colorado does not levy a state property tax; mills are levied and collected locally (county / municipal / district). If a program has a state statute or state agency framework, say that in **What is it?** and use a level like `Local levy (state program)` so Government type never implies the mill is a statewide state tax.
- **detail** — Optional. Only for **type** or framework hints (e.g. statute article), not for rename / branding / legal vs DBA name (that belongs in **What is it?** briefly, or in **citations**). Avoid unless it truly adds clarity beyond `level`.

## What is it? (`whatIsIt.paragraphs`)

- Follow **Tone and voice (levy explainer copy)** above for phrasing (human-first, citations for formal sources).
- Answers: **What is this entity / program?** (kind of government, role, who it serves.) Prefer **brief** copy; defer detail to the citations accordion and external links.
- Does **not** lead with “part of your property tax…” or “your share…” — that frames the question as “how much is this?” rather than “what is this?”
- **Do not repeat** the authority name from the tile heading (e.g. avoid “Arapahoe Library District is…”). Use a generic lead: “A special district…”, “A local levy that funds a Colorado program…”, “This row funds…”, or refer to “the district shown above” when needed.
- When the program is state-framed, say clearly that the **levy is local**: local governments set the mill rate, and the **county collects it** on the property tax bill. Do not imply Colorado has a state property tax or that the county sets the levy.
- Keep plain language; avoid accountant-style “levy lines” phrasing (see project tone rules).
- **Term links** — Use `{{term:term-id|link label}}` only when the term exists in `termDefinitions.tsx` (and home key terms when applicable). Example: `{{term:term-special-districts|special district}}`. The modal parses these and jumps to the definition.

## Citations (`citationBlocks`)

- Prefer statute / official framework + agency or district overview (same general pattern as DD).
- Links must be `http://` or `https://` (validator enforces).

## Matching (`match`)

- Prefer **stable Mart line code** (`levyLineCode`) when the bundled stacks use a unique code for that row.
- `lgId` and `labelContainsAll` support documentation and fallbacks; **same LG ID** can appear on multiple rows — do not rely on LG ID alone.
- Run `npm run validate:levy-explainer` before merge; `npm run build` runs it via `prebuild`. The validator rejects em dashes in explainer copy (see House rules).
- Coverage planning: `python3 tools/list_levy_explainer_queue.py`

## House rules

- ASCII quotes and apostrophes only in JSON and docs (no smart quotes).
- **Em dash (U+2014):** Not allowed in resident-facing strings in `levy-explainer-entries.json` (enforced by `tools/validate_levy_explainer_entries.mjs`). Use comma or period.
